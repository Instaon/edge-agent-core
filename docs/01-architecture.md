# 架构与运行流程

本文档描述 `edge-agent-core` 的整体分层与主循环的完整执行路径。对应实现见 [src/kernel.rs](../src/kernel.rs)。

## 1. 分层架构

```
                外部事件 / 指令（语音、传感器、定时器、API）
             业务侧自行接入，框架不关心事件如何产生
                              │
                              ▼
                 ┌────────────────────────┐
                 │      统一事件入口        │   EventQueue（优先级堆）
                 │      event.rs           │   业务定优先级，内核只按序执行
                 └────────────┬───────────┘
                              │ pop
                              ▼
                 ┌────────────────────────┐
                 │        主循环           │   kernel.rs :: handle_event / execute
                 │  （单线程、同步、常驻）  │   常驻进程 + Loop，不是一问一答
                 └────────────┬───────────┘
                              │
              ┌───────────────┼───────────────────┐
              ▼               ▼                    ▼
     ┌────────────────┐ ┌────────────┐   ┌──────────────────┐
     │  资源锁          │ │  上下文     │   │   熔断器           │
     │  lock.rs        │ │  context.rs │   │   breaker.rs      │
     │  同一设备任一时刻 │ │  硬字节预算 │   │  连续失败/重复动作 │
     │  只被一个任务持有 │ │ 超限丢最旧  │   │  强制中断进入降级  │
     └────────────────┘ └────────────┘   └──────────────────┘
                              │
                              ▼
                 ┌────────────────────────┐
                 │    Wasm 插件运行时      │   plugin/runtime.rs
                 │  （沙箱、燃料、内存上限）│   plugin/registry.rs（分发/回滚）
                 └────────────┬───────────┘
                    ┌─────────┼─────────┐
                    ▼         ▼         ▼
              生命周期插件  工具插件   策略插件
              (hook)       (tool)    (strategy)
                              │
                              ▼
                 ┌────────────────────────┐
                 │     推理后端接口         │   inference.rs
                 │  Mock / OpenAI 兼容 /    │   业务可实现 trait 接入
                 │  业务自定义 C-ABI 等      │   任意本地推理库
                 └────────────────────────┘
                              │
                              ▼
              本地模型推理 ──▶ 工具插件 ──▶ 物理设备 / 本地网络
```

内核本身不包含上图之外的任何东西——没有触发源实现、没有物联协议、没有分发服务端。这些都是业务层或工具插件要做的事。

## 2. 主循环：一个事件的完整生命周期

每个事件从 `EventQueue::pop` 出队开始，到产出 `TaskOutcome` 结束。整个过程是一条**确定性降级链**：模型能不能用、插件在不在、网络通不通，链条上每一级都有明确的下一步，永远不会卡死在中间状态。

```
event
  │
  ▼
[pre_task 生命周期钩子]  ──▶ 所有 kind=hook 且声明 hooks 含 "pre_task" 的插件依次执行
  │                          （单个钩子失败只记日志，不影响主流程）
  ▼
┌─────────────────────────────────────────────────────────┐
│ 1. 策略路由（有 strategy 插件才走这一步）                    │
│    strategy.route(event) -> decision: "rule" | "model"     │
│    [post_route 钩子] 携带最终 decision（rule/model/none）    │
│                                                              │
│    decision=rule  ──▶ 规则直达，不经过模型，直接产出 reply    │
│    decision=model 或无策略插件 ──▶ 进入第 2 步               │
└─────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ 2. 熔断器闸门                                                │
│    breaker.is_open() == true ──▶ 直接跳到第 5 步（降级）      │
│    否则继续                                                   │
└─────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ 3. 模型路径（最多重试 max_format_retries 次，每次重试都重走 a）│
│                                                              │
│    a. [pre_infer 钩子]（携带 attempt 序号）                    │
│       backend.generate(system, context, input) -> raw text  │
│       推理失败 ──▶ 记录错误，重试                              │
│       [post_infer 钩子] 携带原始输出（格式校验前，可观察到      │
│       乱码和非法 JSON —— 模型行为监控的唯一位置）              │
│                                                              │
│    b. parse_model_command(raw)                              │
│       内核原生 JSON 校验：必须是恰好 {reply} 或 {tool,args}    │
│       非法格式 ──▶ 记录错误，重试（输出格式强制纠偏）           │
│       [on_plan 钩子] 携带解析出的合法命令（执行前审计点）        │
│                                                              │
│    c. 熔断器记录本次动作指纹（reply/tool/args 的哈希）          │
│       与上次相同且达到 max_repeats ──▶ 判定死循环，跳第 5 步    │
│                                                              │
│    d. {reply: "..."}  ──▶ 直接产出，任务结束                  │
│       {tool: "x", args} ──▶ 进入第 4 步                       │
│                                                              │
│    重试全部耗尽 ──▶ 记录一次熔断失败，跳第 5 步                │
└─────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ 4. 工具调用                                                  │
│    a. 工具插件不存在 ──▶ 记录失败，跳第 5 步                   │
│    b. 提取工具 manifest 中 "device:*" 权限项，尝试一次性         │
│       acquire_all（全有或全无）                                │
│       资源被占用 ──▶ 立即返回 busy（不排队、不抢占）             │
│    c. [pre_tool 钩子]（锁已到手，设备操作审计点）                │
│       调用插件（见下方"插件调用统一漏斗"）                       │
│       [post_tool 钩子] 携带 ok/error（无论成败都触发）           │
│       成功 ──▶ 产出 reply，任务结束                            │
│       插件返回失败 / 崩溃 / 超预算 ──▶ 记录失败，跳第 5 步       │
│    d. 无论成功失败，任务结束时释放该任务持有的所有资源锁          │
└─────────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ 5. 降级（规则保底 → 安全拒绝）                                │
│    [on_degrade 钩子] 携带降级原因（设备健康监控的核心信号）      │
│    再次调用策略插件，phase="fallback"                         │
│    策略给出 decision=rule 的确定性回答 ──▶ 使用该回答            │
│    否则 ──▶ status=rejected，明确报错原因，绝不静默挂起          │
│    熔断器在此处被重置，避免一次降级后永久锁死                    │
└─────────────────────────────────────────────────────────┘
  │
  ▼
[post_task 生命周期钩子]  ──▶ 携带最终 outcome {status, reply, via}
  │
  ▼
[on_rollback 钩子排空]  ──▶ 本任务期间若有插件被自动回滚，在此逐个通知
  │                         （延迟到任务边界触发，避免在插件调用内递归）
  ▼
写入上下文（user + assistant 各一条，受 context_max_bytes 硬预算约束）
  │
  ▼
TaskOutcome { status, reply, via }
```

任务级流程之外还有两个内核级挂载点：`kernel_start`（内核启动、插件扫描完成后）和 `kernel_stop`（业务调用 `Kernel::shutdown` 时），全部 12 个挂载点的清单和各点携带的数据见 [03-usage.md](03-usage.md)。

`status` 取值：`ok`（正常完成）/ `busy`（资源被占用，拒绝而非排队等待）/ `rejected`（降级链兜底后仍无法处理）/ `error`（内核级异常，如插件重载失败）。
`via` 标明答案来自哪一级：`rule` / `model` / `tool` / `fallback` / `kernel`。业务日志和排障应始终关注这个字段。

## 3. 插件调用统一漏斗

无论是生命周期钩子、工具插件还是策略插件，最终都汇入同一个函数 `Kernel::invoke_plugin`（[kernel.rs](../src/kernel.rs)），保证权限裁剪、执行预算、健康统计三件事永远不会被绕过：

```
invoke_plugin(name, input)
  │
  ├─ 1. 从 Registry 取已加载插件（找不到直接报错，不会静默跳过）
  │
  ├─ 2. 权限裁剪 PluginInput
  │     manifest.permissions.context == true ？
  │       是 ──▶ 附上下文只读副本
  │       否 ──▶ context 字段保持 None，插件从数据结构上就看不到
  │
  ├─ 3. PluginRuntime::invoke（沙箱执行，见 03-usage.md 的 ABI 一节）
  │     - 全新 Store，不与其他调用共享状态
  │     - plugin_fuel 燃料预算（执行时长配额）
  │     - plugin_memory_limit 线性内存硬上限
  │     - host_call 逐次比对 manifest.permissions.capabilities 裁决
  │     - 返回值必须严格匹配 PluginOutput 信封（deny_unknown_fields）
  │
  └─ 4. Registry::report_result（健康统计）
        成功 ──▶ 连续失败计数清零
        失败 ──▶ 计数 +1，达到 plugin_max_failures ──▶
                 写 .disabled 标记 + 自动 reload 回滚到上一版本
```

## 4. 并发与资源竞争

内核是**单线程同步主循环**：`run_pending()` 逐个 `pop` 事件顺序处理。这本身就是并发仲裁的第一层——不存在两个任务同时跑的情况。

在此基础上，`ResourceLocks`（[lock.rs](../src/lock.rs)）解决的是"任务内部对物理设备的占用"问题：一个工具调用声明了 `device:relay0`，执行期间这把锁归当前任务持有；如果同一资源已被占用（理论上只会发生在未来引入并发执行模型时，或工具嵌套调用时），内核**立即返回 busy，不排队、不抢占**。要不要重试、要不要抢占，是业务在收到 `busy` 之后自己决定的策略，不是内核的职责。

## 5. 稳定性防线如何互相配合

三道防线不是孤立的，而是一条链：

| 防线 | 触发条件 | 直接后果 |
| --- | --- | --- |
| 格式校验 | 模型输出不是合法的 `{reply}` / `{tool,args}` | 有限次重试 |
| 熔断器 | 重试耗尽 / 连续任务失败达阈值 / 连续重复同一动作 | 强制跳转降级，阻止继续消耗推理资源 |
| 降级链 | 熔断触发，或工具/插件失败 | 策略插件规则兜底，仍不行则安全拒绝并报错 |

内存预算（`context.rs`）和执行预算（`plugin/runtime.rs` 的燃料与内存上限）是横切于整条链路的硬约束，不需要任何逻辑触发——它们是数据结构和沙箱本身的物理限制，因此"永不 OOM、永不被单个插件拖垮"这句话不依赖任何检测逻辑是否生效。
