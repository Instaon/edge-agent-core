# 核心模块设计与理念

本文档逐模块说明"为什么这样设计"，而非重复代码里已经写清楚的"做了什么"。每一节先给设计理念，再给关键实现取舍。

## 设计总纲：机制进内核，策略给业务

一个能力要进内核，必须同时满足三条：

1. 所有业务都需要它；
2. 它在内核外无法正确实现（安全性质必须由底层保证）；
3. 缺了它，"不死机、不失控"的承诺就不成立。

凡是"怎么做更好"的判断——优先级怎么定、要不要抢占、断线要不要重试——都不在内核里，因为答案因业务而异。凡是"必须保证"的判断——内存不能爆、插件不能越权、信号不能篡改——都在内核里，因为一旦交给业务自觉遵守，防线形同虚设。

这条总纲落到组件上，就是一条清晰的可替换边界：**安全相关和 Loop 相关的钉死在内核，其余一切皆可 Wasm 化**——框架自带一套基础实现保证开箱即用，但每一个非内核环节都能被 wasm 插件替换：

| 钉死在内核（安全 + Loop） | 可 Wasm 化（括号内为框架自带的基础版） |
| --- | --- |
| 事件循环与队列 | 路由与规则逻辑（无策略插件时全部走模型） |
| 资源锁与并发仲裁 | 执行能力（无工具插件时模型只能纯对话） |
| 熔断器 | 生命周期观察（不挂钩子就是纯净主循环） |
| 内存预算 | 推理接入（自带 Mock / OpenAI 兼容，`backend.type=plugin` 切到 wasm） |
| 验签、权限裁决、健康统计与回滚 | 格式修复（自带严格 JSON 校验，`repair_plugin` 挂 wasm 修复器） |
| 基础 JSON 校验的**最终裁决权** | 保底回复（策略插件的 fallback 阶段） |

注意最后一行的不对称：格式修复可以外包给 wasm，但修复结果**必须重新通过内核自己的严格校验**——修复插件只能帮内核"救回"输出，永远不能放宽内核接受什么。这是"安全留内核"原则在单个功能内部的体现。

## 1. 事件队列（[event.rs](../src/event.rs)）

**理念**：内核不关心事件从哪来，只保证"先到先服务、优先级说了算"这一条契约。

`EventQueue` 是一个按 `(priority, 到达顺序)` 排序的二叉堆。`priority` 由业务自行赋值——传感器告警可以标高优先级，普通语音指令标默认优先级——但去重、合并、"这个事件该不该现在处理"完全是业务在入队前要做的判断。内核只负责：谁优先级高谁先出队，同优先级先进先出。

这是"内核只提供机制，不提供策略"最直接的例子：队列结构（机制）是内核的，排序权重的语义（策略）是业务的。

## 2. 上下文（[context.rs](../src/context.rs)）

**理念**：内存预算是硬约束，不是建议。

`Context` 是一个有硬字节上限的双端队列。每次 `push` 都会检查累计字节数，超限就从队首丢最旧的条目，直到回到预算内。单条超大条目也不能绕过预算——会被直接截断到预算允许的长度。

这里刻意没有做"更智能"的裁剪（比如摘要旧对话、按语义重要性保留）——那是压缩策略，压缩策略本身也要消耗算力和时间，并且"什么重要"是业务判断。内核只保证一件事：**无论上游怎么灌数据，内存占用永远有上限**，多余的智能留给未来的钩子或插件。

## 3. 资源锁（[lock.rs](../src/lock.rs)）

**理念**：设备控制的并发安全，只有宿主能保证；抢占策略，只有业务能定义。

`ResourceLocks` 是一个 `资源名 -> 持有任务 ID` 的映射，`acquire_all` 是全有或全无的原子操作——要么这次调用需要的所有设备资源都拿到手，要么一个都不占用直接失败。这避免了经典的"拿到一半锁"死锁场景。

刻意不做抢占：抢占意味着要能安全地中断一个正在执行的任务并回滚其副作用（比如设备已经转了一半的动作），这在框架层面无法通用地做对——"能不能中断"和"中断后怎么收拾"是每个工具插件自己的业务语义。内核给的是最基础但绝对可靠的原语：**同一时刻，一个物理资源只服务一个任务**，冲突时诚实地告诉调用者"忙"，选择权交出去。

## 4. 熔断器（[breaker.rs](../src/breaker.rs)）

**理念**：用最简单、最不可能出错的机制换取最强的确定性保证。

熔断器只有两类计数器：连续失败次数、连续相同动作次数。没有滑动窗口、没有概率模型、没有超时衰减曲线——因为这些复杂机制本身可能出 bug，而熔断器是"系统失控时的最后一道闸"，它自己必须比它保护的东西更简单、更不容易坏。

两个触发条件对应两类失控：

- **连续失败**：模型或插件持续给不出可用结果（推理报错、格式非法、工具报错）；
- **连续重复动作**：模型输出"合法但无意义"，比如反复规划同一个不会成功的工具调用——这是格式校验抓不住的死循环,只能靠行为指纹去识别。

熔断触发后必须显式 `reset()`（在降级完成后由内核调用），不会自愈计时——宁可多打断一次，也不允许熔断器在系统真正稳定前悄悄放行。

## 5. 推理后端（[inference.rs](../src/inference.rs)）

**理念**：模型调用是运行时的一个可替换环节，不是内核的固定组成部分。

`InferenceBackend` 是一个只有一个方法的 trait：给定 system prompt、上下文、输入，返回一段文本。内核不关心这段文本从哪来——本地 llama.cpp 的 C-ABI 绑定、厂商 NPU runtime、局域网内的 OpenAI 兼容服务，甚至由 Wasm 插件代理转发，全都是同一个 trait 的不同实现。

框架原生提供两个实现打底：

- `MockBackend`：确定性回显，不依赖任何模型即可跑通整个内核逻辑，是这个框架能"无模型冒烟测试"的原因；
- `OpenAiBackend`：对接任何讲 OpenAI chat-completions 协议的本地/局域网服务（llama.cpp server、ollama、厂商网关等），覆盖了多数端侧场景不需要业务自己写胶水代码。

除原生 trait 实现外，配置 `backend.type = "plugin"` 可以把推理整个交给一个 wasm 插件（`InferencePath::Plugin`）：内核以 `kind: "infer"` 调用它，插件通过 `host_call` 的能力（net、厂商 NPU 桥接等）触达真正的推理引擎。这条路径走的是和其他插件完全相同的 `invoke_plugin` 统一漏斗——上下文按 manifest 权限裁剪、燃料与内存预算、健康统计与回滚都照常生效，推理插件连续失败同样会被自动禁用。

**C-ABI 直连**没有内置一个具体实现，因为不同推理库的 C-ABI 形状千差万别，内置任何一个都是过度设计。正确的做法是业务实现 `InferenceBackend`，在实现内部调用具体的 C-ABI（`extern "C"` 绑定），装配到 `Kernel::new` 里。framework 保证的是"这一环随时能换"，不是"这一环内核帮你写好"。

## 6. Wasm 插件系统

这是整个框架里设计考量最多的部分，拆成四块说。

### 6.1 为什么是 Wasm 沙箱（[plugin/runtime.rs](../src/plugin/runtime.rs)）

**理念**：故障隔离和资源隔离必须由宿主强制，不能指望插件自律。

选 Wasm 而不是进程隔离或动态库加载，是因为它同时满足两个边缘设备特有的约束：

- **足够轻**：Wasm 模块几十 KB 到几百 KB，不像子进程那样有固定的内存/调度开销，适配 2GB–8GB 设备跑多个插件；
- **能力默认为零**：Wasm 沙箱天生没有系统调用能力，插件想访问文件、网络、硬件，唯一路径是宿主主动开的 `host_call` 这一扇门。这比"动态库加载后再靠约定俗成不越界"可靠得多——越界在 Wasm 里是做不到，而不是不应该。

实现上的两个关键取舍：

- **每次调用全新 Store**：不复用状态，杜绝"上一次调用的脏数据影响这一次"，代价是启动开销，但插件调用本来就不追求高频（毫秒级 wasmtime 实例化对边缘场景足够快）；
- **燃料（fuel）而非墙钟超时**：`consume_fuel` 让"执行时长配额"变成确定性的指令计数，而不是依赖系统时钟——这与"内核只做确定性的事"一脉相承，同样的输入永远消耗同样的燃料，不受宿主机瞬时负载影响。

### 6.2 三类插件为什么是这三类

**理念**：所有可能进沙箱的东西，本质上只有三种关系——挂钩子、给能力、定逻辑。

- **工具插件（tool）**：回答"能做什么"——硬件驱动、协议对接、具体操作；
- **策略与工作流插件（strategy）**：回答"该不该经过模型"——既能让 Agent 完全脱离模型走确定性规则（省算力、保稳定），也能做路由判断，同时它是降级链的保底承接层，这是它和"工具插件"本质的区别：工具插件被模型调用执行，策略插件决定要不要调用模型；
- **生命周期插件（hook）**：回答"在框架的某个时间点该做点什么"——不参与决策，只做观察和旁路处理（状态上报、审计、指标采集）。

三者不是并列的功能列表，而是内核主循环三个必然要有的挂载点：路由决策挂 strategy，具体执行挂 tool，横切关注点挂 hook。没有第四类，是因为主循环里不存在第四种角色。

#### 生命周期：确定性链条的完整投影

生命周期不是"找几个方便的地方放钩子"，而是一条设计原则：**主循环的每一个阶段边界、每一次关键异常，都必须外化成一个挂载点**。降级链是内核的骨架，生命周期就是这条骨架对外的完整投影——缺一个点，设备厂商的监控就有一段盲区。

由此推导出三层共 12 个点（完整清单和各点携带的数据见 [03-usage.md](03-usage.md)）：

- **内核级**（`kernel_start` / `kernel_stop`）：进程本身的生与死，插件初始化和状态落盘的时机；
- **任务级**（`pre_task` → `post_route` → `pre_infer` → `post_infer` → `on_plan` → `pre_tool` → `post_tool` → `post_task`）：一个事件从出队到产出结果所经过的每一道阶段边界。相邻两个点之间恰好是主循环的一个处理阶段，所以这组点既是监控探针，也是理解内核流程的地图；
- **异常事件**（`on_degrade` / `on_rollback`）：不属于正常时序、但对设备健康至关重要的时刻——链条降级和插件回滚。它们单列而不并入任务级时序，因为"发生了"本身就是信号。

两个刻意的设计约束：

1. **钩子是观察者，不是拦截器。** 钩子的返回值不影响主流程，失败只记日志。这不是能力缺失，而是确定性保护：如果任意插件能在任意阶段改写流程，降级链的"每一级都可预期"就不成立了。想改变流程的扩展有明确归属——路由和保底写策略插件，执行写工具插件。
2. **`on_rollback` 延迟到任务边界触发。** 回滚发生在插件调用内部（健康统计判定时），如果就地触发钩子，钩子本身又是插件调用，可能无限递归。内核把回滚通知暂存，在任务结束等安全边界统一发出——这是"机制必须由内核保证"的又一个例子：递归防护不能指望钩子作者自觉。

### 6.3 ABI 与输入输出边界（[plugin/abi.rs](../src/plugin/abi.rs)）

**理念**：插件永远只能看到内核主动给它的序列化副本，绝不能触达内核内存本身。

数据流向：

```
内核侧                          沙箱边界                        插件侧
PluginInput (Rust struct)  ──序列化为 JSON──▶  guest 内存拷贝  ──▶  ea_handle 解析

PluginOutput (严格信封)    ◀──guest 写回──   guest 分配的内存  ◀──  插件产出 JSON
```

三个关键设计点：

1. **权限先于数据**：`PluginInput.context` 字段是否有值，在数据离开内核之前就已经由 manifest 的 `permissions.context` 决定了。插件代码里根本不存在"context 字段有但我选择不用"的情况——没声明权限，这个字段从数据结构层面就是空的。这比"传了但约定不看"安全得多。

2. **输出必须是严格信封**：`PluginOutput` 用 `#[serde(deny_unknown_fields)]`，多一个字段、少一个必需字段、类型不对，整体判定为非法输出直接丢弃（并计入插件失败）。这是刻意的：端侧设备没有余力去"尽量理解"一个格式不规范的插件输出，宁可拒绝也不猜测。

3. **能力调用是唯一的越界通道**：插件不能直接拿到文件句柄或 socket，只能构造一个 `{cap, op, args}` 请求，通过 `host_call` 这一个宿主函数发出去。内核每次调用都现查 manifest 里声明了没有——不是加载时检查一次就放行，是**逐次裁决**。业务侧要实现 `HostBridge` trait 来决定这些能力请求具体怎么执行（连哪个串口、调哪个本地网关）；内核自带的 `NullBridge` 默认拒绝一切，保证不接业务代码时框架本身是全封闭的。

### 6.4 分发规范与生命周期（[plugin/manifest.rs](../src/plugin/manifest.rs)、[plugin/registry.rs](../src/plugin/registry.rs)）

**理念**：框架不做分发服务，但分发的"规范"必须是框架原生定义并强制执行的，否则"零信任"就是一句空话。

**签名覆盖什么**：不只签 wasm 二进制，而是把 `name + version + kind + hooks + context 权限 + capabilities 列表 + wasm 的 sha256` 一起规范化成一段 canonical JSON 再签名（见 `Manifest::signing_payload`）。这意味着攻击者即使能连同 wasm 一起替换 manifest，只要没有私钥，就无法让插件"看起来"权限更小、实际权限更大，或者把工具插件伪装成策略插件。**代码和权限声明是同一个签名单元**，这是防止"事后篡改声明来提权"的关键设计。

**为什么目录结构即数据**：插件包在磁盘上是 `plugins/<name>/<semver>/{plugin.wasm, manifest.json}`，加载时会核对目录名和 manifest 里的 `name`/`version` 是否一致（`load_version` 里的 `ensure!`）。这避免了"文件系统里的名字"和"清单里签名的名字"不一致导致的混淆攻击——哪怕两者都各自合法，不匹配就拒绝。

**版本选择即热更**：`Registry::scan`/`reload` 总是在一个插件名下选**验证通过且未被标记 `.disabled` 的最高 semver**。热更新不是"推送一个特殊指令切换版本"，而是纯粹的"新版本目录出现了，下次 reload 自然选中它"。这带来一个重要的语义：**在途任务持有的是已经取出的 `Module` 句柄，不受这次 reload 影响，跑完为止；下一个任务发起 `invoke_plugin` 时才会用到 reload 后的新版本**——这就是"静默热更新、不打断当前任务"在代码里的落地方式，不需要额外的版本锁或者引用计数。

**回滚是自动的、状态化的**：`Registry::report_result` 在每次插件调用后记录成功/失败，连续失败达到阈值就在磁盘上写一个 `.disabled` 标记（持久化，重启也认）并立即 `reload` 回退到（未被标记的）次高版本。回滚不需要人工介入，也不需要中心化的控制面——这是"故障插件自动回滚"在没有云端管控时依然成立的原因。

## 7. 安全模型如何落地

对照 README 的"安全模型"一节，代码里的对应关系：

| README 承诺 | 落地位置 |
| --- | --- |
| 设备不能崩：内存预算 | `context.rs` 硬字节上限 + `plugin/runtime.rs` 的 `StoreLimits` 内存上限 |
| 设备不能崩：熔断 | `breaker.rs` |
| 设备不能崩：沙箱隔离 | `plugin/runtime.rs` 每次调用独立 Store + fuel 配额 |
| 插件默认零权限 | `plugin/abi.rs` 的 `PluginInput` 按权限裁剪、`NullBridge` 默认拒绝一切 |
| 声明 → 签名绑定 | `Manifest::signing_payload` 把权限声明纳入签名范围 |
| 加载审校 | `registry.rs::load_version` 校验签名 + 目录一致性 |
| 运行时逐次裁决 | `runtime.rs::handle_host_call` 每次比对 `allowed_caps` |
| 异常处置（禁用+回滚） | `registry.rs::report_result` |

安全不是某一个模块，而是这条链每一环都不可绕过——任何一环被跳过，整条链就形同虚设，所以这些检查全部在框架的必经路径上（`invoke_plugin` 统一漏斗），而不是散落在各处等业务记得调用。
